# Архитектура «Настольные игры по сети»

## Обзор

Клиенты 1С обмениваются состоянием партии через **общую сетевую папку** (JSON-файлы).  
Полноценный HTTP/WebSocket-сервер в внешней обработке без отдельной службы недоступен; вместо него используется модель **«авторитетный файл + revision»**:

1. Клиент читает партию.
2. Меняет состояние локально (правила проверяются кодом обработки).
3. Пишет файл только если `версия` на диске совпала с ожидаемой.
4. Атомарная запись: `.tmp` → удаление цели → `ПереместитьФайл`, плюс `.lock`.

Хост дополнительно фиксирует таймауты, пропавших по пульсу и старт матча в дураке.

## Жизненный цикл партии

```
создание (хост) → ожидание / лобби → игра → завершение → (опц.) снова лобби (дурак)
                      ↑________________ переподключение по PlayerID / имени
```

Файлы:

| Файл | Назначение |
|------|------------|
| `shashki_*.json` / `chess_*.json` / `durak_*.json` | Состояние партии |
| `*.json.lock` | Кратковременная блокировка записи |
| `hb_<код>_<индекс>.pulse` | Пульс игрока (alive) |
| `rooms_index.json` | Список комнат в папке |

## Формат JSON партии (схема 2)

Обязательные поля:

- `схема` — версия схемы (сейчас **2**), миграция при чтении
- `id`, `версия` (revision), `типИгры`, `статус`, `доска`, `ходБелых`
- `игроки[]`, `идИгроков[]` — имя и уникальный PlayerID
- `парольХеш` — пусто = без пароля
- `журнал[]` — `{t,pid,rev,act,ok,d}` (до 200)
- `чат[]` — `{t,name,pid,text}` (до 50, текст ≤ 200)
- `ходНачатМс`, `ходЛимитСек` — авторитетный таймер хода
- `созданоМс`, `обновленоМс` — для очистки

Старые партии без новых полей поднимаются функцией `МигрироватьСостояниеПартии`.

## Протокол хода

```
Клиент A: read → expectedRev=N → apply move → version=N+1 → lock+atomic write
Клиент B: если на диске уже N+1 → «ход устарел», перечитать
```

Проверка правил:

- шашки / шахматы — генерация легальных ходов (`ХодШапкиЛегален` / `ХодШахматЛегален`);
- дурак — `ОбработатьКликДурака` отклоняет нелегальные действия.

Без выделенного сервера клиент всё ещё может подменить файл вручную; revision и журнал снижают случайные гонки и помогают разбору инцидентов.

## Идентификация

При старте формы создаётся `ИдИгрока` (UUID без дефисов).  
Он пишется в `идИгроков` при создании/входе. Переподключение ищет сначала по ID, затем по имени.

## Таймер

В JSON хранится `ходНачатМс` (универсальные мс).  
Остаток: `ходЛимитСек - (now - ходНачатМс)/1000`.  
Просрочку в сети фиксирует хост (и игрок на своём ходе). Локальный таймер — запасной отображатель.

## Расширение

1. Новые поля — в `НовоеСостояниеПартии` + `JSONВСостояние` + `МигрироватьСостояниеПартии`, поднять `ВерсияСхемыПартии`.
2. Новая игра — префикс файла в `ИмяФайлаПартии`, ветки в форме.
3. Будущий HTTP-сервер — заменить только слой чтения/записи; правила и UI оставить.

## Структура кода

- `Ext/ObjectModule.bsl` — правила игр, JSON, сетевые хелперы (`#Область СетевойСлойИНадёжность`)
- `Forms/Форма` — UI, опрос 1 с, файловый I/O, пульс, чат, индекс комнат

Полное разбиение на отдельные общие модули конфигурации потребует встраивания в конфигурацию (не только `.epf`).
